## 1. Цель и рамки

Свести два независимых приёмщика ошибок в один бот (LarkBot) с поддержкой двух складов.

**В рамках:**

- перенос флоу и таксономии `test bot` (`telegram_photo_bot/`) внутрь LarkBot;
- вывод из эксплуатации дерева решений LarkBot (`equipment_intake` → `tree_config/engine/keyboards/types/storage/editor`);
- единая запись завершённого отчёта в `exceptions_glpc` + карточка Lark по складу;
- разделение по складам GLP-C / SMALL-P3 через топики Telegram.

**Вне рамок:**

- изменения в веб-UI и отчётности `tk-assist-api` (кроме, при необходимости, одного поля);
- пересмотр сменных метрик, `/top`, дайджестов;
- миграция исторических записей `telegram_equipment_reports`.

## 3. Целевая архитектура

```
Telegram, топик ошибок GLP-C ─┐
Telegram, топик ошибок SP3  ─┤
                              ▼
        telegram_bot.py → set_current_warehouse(warehouse_for_thread(...))
                              ▼
        equipment_intake.flow.start(chat, sender, image, message_id, warehouse)
                              ▼
        ┌──────────── таксономия из test bot (taxonomy.py) ───────────┐
        │  категория → модель → модуль → номер → описание → подтверждение │
        └──────────────────────────────────────────────────────────────┘
                              ▼  (сессии: durable-store)
                      report_completion
                    ┌──────────┼──────────┬───────────────┐
                    ▼          ▼          ▼               ▼
            exceptions_glpc  Lark card  Supabase      (опц.)
              (rest_post)   по складу   Storage      локальный
                            (hook)     → photo_url    JSONL
```

**Ключевой приём:** оставить в `telegram_bot.py` те же три точки входа —
`flow.start`, `flow.handle_callback`, `flow.handle_text` (уже вызываются в строках
4016, 1852, 4486). Тогда проводка бота почти не меняется, а движок внутри заменяется.
Это резко сокращает радиус поражения при переписывании 5203-строчного файла.

## 4. Ключевые решения

| # | Решение | Рекомендация | Почему |
|---|---|---|---|
| D1 | Куда писать `exceptions_glpc` | **Напрямую из LarkBot** через `rest_post` | Убирает блокер `warehouse: "GLP-C"` в API; LarkBot уже пишет туда в legacy-флоу; нет лишнего сетевого хопа и секрета |
| D2 | Таксономия выбора | **По складам, подписи человеческие, тип канонический** | Обе готовые таксономии не совпадают с данными (§2.1); карта подписей выведена из данных (§2.5) |

| D2b | Детальные данные | **Писать обе таблицы**: `exceptions_glpc` + `telegram_equipment_reports` | Решение заказчика; `answers`/`path` — материал для будущих готовых вариантов |
| D3 | Хранение сессий | **Таблица в Supabase** | Railway без volume: `sessions.json` не переживёт редеплой. В памяти — потеря незавершённых отчётов |

| D5 | `uniq_key` | `telegram-photo-bot:<user_id>:<имя_файла>` | Идемпотентно при повторной доставке апдейта, не пересекается с legacy-форматом |
| D5a | QR Floor | **X → Y → Zone** (три шага) | Решение заказчика; карта проблем по координатам |
| D6 | Судьба `/tree`, `editor`, `storage` | **Вывести** | Ниже D2: дерево решений больше не источник флоу |
| D7 | Транспорт Lark | `lark_hooks` + `lark_media` (LarkBot) | Роутинг по складу, HMAC, фолбэк на ссылку при исчерпании квоты |

| D9 | Standalone-бот на Mac | **Вывести** после cutover | Иначе два бота конкурируют за один смысл |
| D10 | Склад | **Только из топика**, никогда из номера | Номера 121/122/123 есть в обоих складах (§2.4); так уже сделано для `/robot` |

### 6.12. Дефекты, найденные охотой на баги (исправлены 2026-10-02)

Все пять найдены адресными проверками кода, каждый закрыт тестом; сами тесты
проверены мутациями (внесение дефекта обратно → тест падает).

**1. Коллизия `uniq_key` теряла отчёты.** Ключ собирался из

строится из координат Telegram (`chat_id` + `message_id`) — одно сообщение

отклоняются, и это выглядит как «бот игнорирует группу».

ещё не выучено; проверяются оба слота. Дополнительно ловятся: два склада на

## 11. Бюджет квоты Lark (10 000/месяц)

### 11.1. Главное: хуки квоту НЕ тратят

Задача сформулирована как «сократить отправки по хукам, чтобы не превысить 10 000».
По коду и документации это **не тот ресурс**:

- `lark_media._hook_post` шлёт в `bot/v2/hook/...` — custom-bot webhook. Он
  **не расходует квоту Open Platform** (явно сказано в `pending_photos.py:4-6`,
  `README_TELEGRAM.md:8` и `PROJECT_MAP.md:15-18`).
- **Единственный вызов, расходующий квоту, — `im/v1/images`** (загрузка фото):
  1 вызов на фото (`lark_media.py:23-25`).

**Следствие: сокращение числа хуков не экономит ни одной единицы квоты.**
Урезав хуки, мы получим более скупой чат, но квота не изменится. Экономить нужно
**загрузки изображений**. Это меняет весь план оптимизации, поэтому фиксирую отдельно.

### 11.2. Кто ещё делит эту квоту

Проверено сравнением `.env`:

| | LarkBot | test bot (standalone) |
|---|---|---|
| `LARK_APP_ID` | **одинаковый** | **одинаковый** |
| `LARK_APP_SECRET` | **одинаковый** | **одинаковый** |

Оба бота работают **под одним Lark-приложением и делят одну квоту 10 000**. Пока
старый бот запущен (LaunchAgent на Mac) и пишет через API, он расходует ту же квоту,
что и LarkBot. Это не гипотеза — в §2.2 найдена его запись в `exceptions_glpc`.

### 11.3. Фактический объём

По `exceptions_glpc`, точные значения через `count=exact`: сентябрь 2026 —
**3889 записей**; октябрь (первые дни) — **378**. Разбивка по складам в окне
2026-09-02…10-02: GLP-C 2981, SMALL-P3 1019.

Фото попадают в Lark картинкой (запись `photo_url` появляется только при фолбэке —
её всего 4), то есть **почти каждое фото в отчёте = 1 вызов квоты**. Guided-флоу
начинается с фото, значит каждый его отчёт тратит 1 единицу.

**Прогноз после подключения SP3:** ~3900 (GLP-C) + ~1000 (SP3) ≈ **4900 загрузок
в месяц**. Это в пределах 10 000, но запас лишь двукратный, и его съедают: второй бот
на том же приложении, повторные отправки одного фото, ручные прогоны и рост объёма.
При ~4900/мес лимит будет достигнут уже при удвоении отчётности.

### 11.4. Что реально экономит квоту

Ранжировано по отдаче на единицу усилий.

1. **Остановить standalone test bot** (§D9). Немедленно возвращает его долю расхода —
   сейчас это, вероятно, самая крупная утечка, потому что он дублирует поток.
2. **Кэш `image_key` по хэшу файла.** Сейчас `upload_image()` загружает файл при
   каждом вызове, без памяти о прошлом. На диске уже видно дубли: 16 файлов, 9
   уникальных хэшей. Ключ `sha256 → image_key` (в `bot-reports` или в памяти с TTL)
   убирает повторные загрузки того же фото. Telegram даёт `file_unique_id` в имени
   файла — это готовый ключ дедупликации.
3. **Жёсткий счётчик-предохранитель.** Вести месячный счётчик вызовов `im/v1/images`
   и при достижении порога (например, 8000) **принудительно** переключаться на режим
   «ссылка через Supabase Storage» (0 вызовов). Сейчас переключение происходит только
   *после* отказа API с `99991403` — то есть по факту исчерпания, без запаса.
4. **Не загружать фото там, где оно не нужно.** Служебные и статусные сообщения
   картинок не содержат; проверка, что `upload_image` вызывается только на пути
   отчёта с фото, — дешёвая страховка от лишних вызовов.
5. **Убрать legacy-путь `lark_send.send_text_message`.** Он ходит в
   `im/v1/messages` — расходующий квоту эндпоинт. По документации он «недостижим»,
   потому что `set_notifier` ставится на старте (`telegram_bot.py:5010`), но
   `sendToDataBase.py:84-92` оставляет ветку с вызовом API и лишь пишет warning.
   Достижимость зависит от порядка инициализации — надёжнее удалить ветку.
6. **Проверить частоту запроса токена.** `get_tenant_access_token` кэширует токен на
   `expire - 60` (обычно ~2 ч). Это ~12 запросов в сутки, ~360 в месяц. Немного, но
   если `auth/v3/tenant_access_token/internal` тоже считается в квоте, это заметная
   доля; уточнить у владельца Lark-приложения.
7. **Объединять изображения в одно сообщение.** Если один отчёт несёт несколько
   фото, их можно склеить перед загрузкой — 1 вызов вместо N.

### 11.5. Что квоту НЕ экономит (но полезно по другим причинам)

- **Сокращение числа хуков.** Квота не тратится; выигрыш только в шуме чата.
- **Переход на текст вместо карточек.** Хук всё равно бесплатный.
- **Группировка ошибок в дайджест.** Тоже про читаемость группы.

Эти меры стоит делать, но **не выдавать их за экономию квоты** — иначе бюджет
будет считаться по неверной модели.

### 11.6. Обязательный учёт расхода

- [ ] Дашборд/лог: счётчик `im/v1/images` за календарный месяц по каждому боту.
- [ ] Алерт при 70% и 90% квоты (7 000 и 9 000).
- [ ] Метрика «доля отчётов, ушедших ссылкой» — она же индикатор близости к лимиту.
- [ ] Отдельный прогон: сколько вызовов делает один отчёт end-to-end (сейчас 1, если
      фото одно; подтвердить тестом).

### 11.7. Тесты

- [ ] `upload_image` не вызывается второй раз для того же хэша (кэш).
- [ ] При счётчике выше порога фото уходит ссылкой, `im/v1/images` не вызывается.
- [ ] `sendToDataBase.notify_user` **никогда** не доходит до `lark_send.send_text_message`.
- [ ] Отчёт без фото не порождает вызовов квоты.
- [ ] Один отчёт с одним фото = ровно 1 вызов `im/v1/images`.

### 11.8. Открытые вопросы по квоте

1. **Считается ли `auth/v3/tenant_access_token/internal` в квоту?** От ответа зависит,
   нужна ли экономия ещё и на токене.
2. **Можно ли завести отдельные Lark-приложения** для бота и для отчётов? Тогда квоты
   станут независимыми и риск «один бот съел общий лимит» исчезнет.
3. **Сбрасывается ли квота календарно** или скользящим окном? От этого зависит,
   где ставить порог предохранителя.
4. **Точный объём за полный сентябрь** — запрос упёрся в 4000 строк; нужен
   `count=exact`, чтобы не оценивать бюджет по обрезанной выборке.
