# Telegram-бот приёма ошибок роботов → Lark-группа

Бот переехал с Lark-событий на Telegram. Причина: каждое сообщение в Lark
тянуло за собой вызовы Open Platform API (имя сотрудника, ответ в чат,
скачивание фото), а квота тенанта — 10 000 вызовов в месяц — исчерпана.

Главное: **вывод в Lark-группу идёт через custom-bot webhook**
(`bot/v2/hook/...`), который квоту Open Platform не расходует.

## Как это работает теперь

```
сотрудник → Telegram-группа (бот-админ)
              │  long polling getUpdates
              ▼
        telegram_bot.py
              ├── /reg          → привязка Telegram → employees (Supabase)
              ├── разбор текста → error_parser.parse_error_message
              ├── запись        → Supabase: exceptions + exceptions_glpc
              ├── смена/счётчик  → shift.py + Supabase
              └── вывод         → Lark-группа через webhook (0 вызовов API)
```

| Действие | Было (Lark) | Стало (Telegram) |
|---|---|---|
| Приём сообщений | события `im.message.receive_v1` | long polling Telegram |
| Имя сотрудника | Contact API (вызов) | таблица `telegram_users` (0 вызовов) |
| Ответ в чат («не распознал», алерт) | `im/v1/messages` (вызов) | `sendMessage` в Telegram (0 вызовов) |
| Карточка ошибки в группу | webhook | webhook |
| Скачивание фото | `im/v1/resources` (вызов) | Telegram `getFile` (0 вызовов) |
| Отправка фото в группу | `im/v1/images` (вызов) | `im/v1/images`, а при ошибке квоты — ссылка через Supabase Storage (0 вызовов) |

Фильтр по топику: сообщения принимаются только из топика `Ex GLPC`
(`TELEGRAM_TOPIC_ID`), команды — из любого топика; ответы уходят в топик-источник.

Квоту Lark тратит только загрузка фото, и лишь когда она доступна: при
исчерпанной квоте фото автоматически уходит ссылкой, и тогда расход нулевой.
(В коде остался legacy-путь `lark_send.send_text_message` как fallback
notifier'а: в боте он недостижим — notifier ставится на старте, — и если он
вдруг сработает, в лог уходит предупреждение.)

## Что нужно сделать

### 1. Таблица привязки в Supabase

Supabase → SQL Editor → выполнить `sql/telegram_users.sql`.

### 2. Переменные окружения

Скопировать `.env.example` в `.env` и заполнить:

```
TELEGRAM_BOT_TOKEN=...        # токен от @BotFather
SUPABASE_URL=...
SUPABASE_SERVICE_KEY=...
LARK_APP_ID=...               # только для фото
LARK_APP_SECRET=...           # только для фото
LARK_TARGET_HOOK_URL=...      # webhook целевой группы (по умолчанию уже зашит)
TELEGRAM_TOPIC_NAME=Ex GLPC   # опционально: имя топика
# TELEGRAM_TOPIC_ID=27        # id топика из /id (надёжный фильтр)
```

### 3. Бот в Telegram

1. Токен от [@BotFather](https://t.me/botfather) уже есть — вставить в `.env`.
2. Добавить бота **в группу** и выдать права администратора.
   Privacy mode выключать не нужно: админ получает все сообщения группы
   ([docs](https://core.telegram.org/bots/features#privacy-mode)).
3. Список команд бот публикует сам при старте (`setMyCommands`).

### 4. Топик Ex GLPC (форум-группа)

Бот обрабатывает сообщения **только из одного топика**. Команды `/id`, `/reg`,
`/help` работают в любом топике — чтобы можно было настроиться, а ошибки и
фото принимаются только из нужного.

⚠️ Если **не заданы ни** `TELEGRAM_TOPIC_ID`, **ни** `TELEGRAM_TOPIC_NAME`,
фильтра нет: принимаются сообщения из любого топика и любого чата. При старте
бот громко предупреждает об этом в логе — такую конфигурацию лучше не оставлять
на проде.

Как включить фильтр:

1. Выдать боту **права администратора** в группе (иначе он не видит
   сообщения топиков: privacy mode у ботов включён по умолчанию, но у
   администраторов он не действует).
2. Отправить `/id` **внутри топика `Ex GLPC`** — бот ответит
   `message_thread_id` (например `27`).
3. Вписать его в `.env`:

   ```
   TELEGRAM_TOPIC_ID=27
   ```

4. Перезапустить бота. `/id` в этом топике теперь покажет
   `✅ this topic is monitored (id-match)`.

`/id` и `/help` отвечают даже в чате вне `TELEGRAM_ALLOWED_CHAT_IDS` — чтобы
id всегда можно было узнать, ничего не отключая.

Почему по id, а не по имени: в Bot API **нет** метода, который отдаёт имя
топика по `message_thread_id` (есть только `createForumTopic`,
`editForumTopic`, `getForumTopicIconStickers`). Поэтому `TELEGRAM_TOPIC_NAME`
работает как запасной вариант и только если бот уже видел сервисное сообщение
о создании/переименовании топика (имя запоминается в память процесса).

Ответы бота автоматически уходят **в тот же топик**, откуда пришло сообщение —
включая алерты «отправить в обслуживание» и подтверждения записи.

### 5. Запуск

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python3 telegram_bot.py
```

Проверка: `curl localhost:7777/health` → `{"status":"ok","bot":"..."}`.

### 6. Деплой на Railway

Сервис собран из GitHub и деплоится автоматически по пушу в `main`:

| | |
|---|---|
| Проект / окружение | `adaptable-hope` → `production` |
| Сервис | `glpc-bot-lark` |
| Репозиторий | `Nookons/glpc-bot-lark`, ветка `main` |
| URL | https://glpc-bot-lark-production.up.railway.app |
| Healthcheck | `/health` (задан в `railway.json`) |
| Реплики | 1 (long polling не терпит второй инстанс) |

`railway.json` задаёт команду старта, healthcheck и рестарт по ошибке;
`railway.json` задаёт `build.builder: DOCKERFILE`, healthcheck `/health` и
рестарт по ошибке; команда запуска — в `Dockerfile` (`python3 telegram_bot.py`),
одно место правды. Railway собирает именно Docker-образ (проверено по логам
сборки), поэтому `.dockerignore` защищает образ от попадания `.env`.

Переменные окружения живут в Railway → Variables (`.env` в репозиторий не
попадает): `TELEGRAM_BOT_TOKEN`, `TELEGRAM_TOPIC_ID`, `TELEGRAM_TOPIC_NAME`,
`TELEGRAM_ALLOWED_CHAT_IDS`, `LARK_APP_ID`, `LARK_APP_SECRET`, `SUPABASE_URL`,
`SUPABASE_SERVICE_KEY`, `SUPABASE_PHOTO_BUCKET`, `TELEGRAM_CONFIRM_TTL`.

Обновить переменные из локального `.env` через CLI:

```bash
SVC=glpc-bot-lark
TOKEN=$(grep '^TELEGRAM_BOT_TOKEN=' .env | cut -d= -f2-)
printf '%s' "$TOKEN" | railway variable set TELEGRAM_BOT_TOKEN --stdin --service "$SVC"
railway variable set TELEGRAM_TOPIC_ID=2 --service "$SVC"
```

> ⚠️ Telegram long polling допускает **только один** запущенный инстанс:
> держите 1 реплику и не запускайте бота локально одновременно с Railway,
> иначе в логах будет `Conflict: terminated by other getUpdates request`.

## Команды бота

| Команда | Что делает |
|---|---|
| `/reg Иван Петренко` | привязать Telegram к имени из `employees.user_name` |
| `/whoami` | показать текущую привязку |
| `/unreg` | удалить привязку |
| `/stats [YYYY-MM-DD] [day\|night]` | статистика смены (по умолчанию текущая) |
| `/robot <номер>` | карточка робота: статус, простой, история переходов, ошибки за 7 дней |
| `/digest` | предпросмотр дайджеста обслуживания (те же данные, что уходят в личку) |
| `/top [day\|week\|month]` | топ типов проблем и роботов за период (по умолчанию неделя) |
| `/downtime [дни]` | топ роботов по суммарному простою и MTTR за период |
| `/week` | предпросмотр недельного отчёта |
| `/topics` | какая переменная за какой топик отвечает (настройка/проверка) |
| `/offline <robot>` | отправить робота в офлайн (причина кнопками + описание) |
| `/online <robot>` | вернуть робота в работу (причина + описание) |
| `/cancel` | отменить незавершённую смену статуса |
| `/id` | показать `chat_id`, `user_id`, `message_thread_id`, имя топика и отслеживается ли он |
| `/help` | справка |

При `/reg` имя ищется сначала точно, затем нечётко (rapidfuzz, порог 78) —
при опечатке бот предложит похожие имена из таблицы `employees`.

## Робота нет в системе: подсказка номера и очередь

Сотрудники регулярно присылают номер с опечаткой («3882» вместо «882»). Раньше
ошибка уходила в Lark, номер падал в `robots_to_add`, а записи в базе не
появлялось.

Теперь, если робота нет в справочнике склада, бот сначала ищет похожие номера
(rapidfuzz по номерам склада, порог `ROBOT_FIX_CUTOFF_PERCENT`) и показывает
кнопки:

```
⚠️ Robot #3882 is not in the system.
Is the number correct?
[ ✅ Robot #882 ]  [ ➡️ No, the number is correct ]
```

* нажали похожий номер — ошибка сохраняется обычным путём, как будто номер был
  правильным с самого начала;
* нажали «номер верный» или не ответили `ROBOT_FIX_TTL` секунд — срабатывает
  прежнее поведение: номер уходит в очередь `robots_to_add`, а карточка ошибки —
  в Lark (без пометки, что робота нет в системе).

Подсказку можно выключить (`ROBOT_FIX_SUGGEST=false`) — тогда бот сразу ведёт
себя как раньше.

**Очередь разбирается сама.** Раз в `QUEUE_AUTOCLOSE_INTERVAL` секунд бот
смотрит открытые строки `robots_to_add` и закрывает (`status = true`) те, чьи
номера уже есть в `robots_maintenance_list` — на своём складе или на любом
другом. Проверка 23.09.2026 показала, что из 282 открытых заявок 140 были
такими «потерявшими смысл»: робота добавили, а строку не закрыли. Флаг —
`QUEUE_AUTOCLOSE_ENABLED`.

## Топики: что куда попадает

Группа-форум делится по смыслу. В топике ошибок не должно быть ничего, кроме
ошибок: статусы роботов, статистика и служебные ответы уходят в свои топики.

Бот ведёт **два склада** (`TELEGRAM_WAREHOUSES=glpc=GLP-C,sp3=SMALL-P3`), и у
каждого свой топик ошибок: ошибка, присланная в топик SP3, записывается как
ошибка склада `SMALL-P3` (робот ищется в справочнике этого склада), из топика
GLP-C — как `GLP-C`.

| Топик | Переменная | Что там появляется |
|---|---|---|
| **Ex GLPC** | `TELEGRAM_TOPIC_ID` | ошибки склада GLP-C: текст и фото, «✅ Saved / Photo forwarded», подсказка «робота нет в системе» с кнопками, алерт «отправить в обслуживание» |
| **Ex SP3** | `TELEGRAM_TOPIC_ERROR_SP3` | то же самое для склада SMALL-P3 |
| **Robot status** | `TELEGRAM_TOPIC_STATUS` | `/offline`, `/online`, кнопки причин, «Describe the reason», сообщение о смене статуса, `/robot`, `/cancel`. Склад определяется по самому роботу (номер ищется по обоим складам) |
| **Stats** | `TELEGRAM_TOPIC_STATS` | `/stats`, `/top`, `/downtime`, `/week`, `/digest`; склад — аргументом (`/stats sp3 day`) или склад топика |
| **Service** | `TELEGRAM_TOPIC_SERVICE` | `/help`, `/id`, `/topics`, `/reg`, `/whoami`, `/unreg`, «Unknown command», предупреждения бота |

Топик ошибок для любого склада задаётся как `TELEGRAM_TOPIC_ERROR_<КЛЮЧ>`
(например `TELEGRAM_TOPIC_ERROR_SP3`); для склада по умолчанию работает
историческая `TELEGRAM_TOPIC_ID`.

Ошибки бот принимает **только** из топиков ошибок, команды работают в любом
топике группы.

**Если команду написали в топике ошибок** (а так делают почти всегда),
ответ уходит в её топик, а в топике ошибок остаётся короткая подсказка
«➡️ The answer is in the Stats topic», которая сама удаляется через
`TELEGRAM_CONFIRM_TTL` секунд. Отключить подсказку — `TELEGRAM_MOVED_HINT=false`.
Отключить само разделение (вернуть прежнее поведение «отвечаю там, где
спросили») — `TELEGRAM_ERROR_TOPIC_STRICT=false`.

Значением переменной может быть **id топика** (надёжно) или **имя топика**
(сработает, если бот видел сервисное сообщение о создании/переименовании).

### Как настроить

1. Создать в группе топики: `Ex GLPC`, `Ex SP3`, `Robot status`, `Stats`,
   `Service` (бот-админ умеет создавать их сам — `createForumTopic`).
2. Отправить в каждом топике команду `/id` — бот ответит `message_thread_id`.
3. Прописать в Railway (Variables):

```
TELEGRAM_TOPIC_ID=2                  # Ex GLPC (ошибки GLP-C)
TELEGRAM_TOPIC_ERROR_SP3=318         # Ex SP3 (ошибки SMALL-P3)
TELEGRAM_TOPIC_STATUS=319            # Robot status
TELEGRAM_TOPIC_STATS=320             # Stats
TELEGRAM_TOPIC_SERVICE=321           # Service
TELEGRAM_WAREHOUSES=glpc=GLP-C,sp3=SMALL-P3
```

4. Перезапустить сервис и проверить: `/topics` в любом топике покажет карту,
   а в логах при старте печатается то же самое.

`/topics` дополнительно перечисляет **все топики, в которых бот видел
сообщения** (id + выученное имя). Это самый быстрый способ узнать id: создайте
топик, отправьте в нём что угодно (или `/id`), и он появится в списке. Если
топика в списке нет — бот его ещё не видел.

Пока переменные не заданы, бот работает как раньше: отвечает в топик, откуда
пришло сообщение.

## Дайджест обслуживания (раз в сутки в личку)

Раз в сутки после `DIGEST_HOUR` (по умолчанию 09:00 по Варшаве) бот отправляет
в личку ответственным сводку того, что никто не замечает:

```
🗂 Maintenance digest · 24.09.2026

🔌 Offline longer than 24h: 11
  #135 · 117d · 其他/other
  #123 · 25d · Photoelectric problem of picking up boxes from the car cache
  #3644 · 3d · Abnormal walking
  …

🧾 Open robot-add requests: 133 (new in 24h: 0)
  #3706 · 23.09 01:24
  …
```

* получатели — `ROBOT_ADMIN_TELEGRAM_IDS=111,222`; если переменная пуста,
  дайджест уходит зарегистрированным сотрудникам с `employees.is_leader = true`;
* если сообщать нечего (нет залипших роботов и очередь пуста), дайджест **не
  отправляется** — чтобы не превратиться в ежедневный шум;
* факт отправки пишется маркером в Storage (`bot-reports/<дата>-digest.json`),
  поэтому перезапуск контейнера не даёт второй дайджест за день;
* полностью выключается `DIGEST_ENABLED=false`; порог «залип» —
  `STALE_OFFLINE_HOURS` (по умолчанию 24 часа);
* посмотреть сводку вручную можно командой `/digest` в любом топике.

## Аналитика и недельный отчёт

`/top` и `/downtime` читают те же таблицы, что отчёт смены, но за длинный
период (данные берутся постранично — PostgREST отдаёт не больше ~4000 строк
за запрос, и «взять всё» одним запросом означало бы молча обрезанный отчёт).

Пример:

```
📈 Top for the last 7 day(s) · GLP-C
Total: 464 exceptions

🗂 Issues:
  311 · Unable to drive
  83 · Abnormal pick-up and delivery

🤖 Robots:
  13 · #3750

🛠 Downtime · last 7 day(s) · GLP-C
Repairs started: 18 · MTTR 23h 40m
Also closed: 27 older repair(s) · longest #132 2170h 53m
```

Важно про MTTR: он считается только по ремонтам, которые **начались и
закончились внутри периода**. Иначе закрытие старой заявки (робот стоял
месяцами) раздувает среднее — такие заявки показаны отдельной строкой
«Also closed». Роботы, которые всё ещё в офлайне, в MTTR не попадают.

Недельный отчёт в Lark-группу (`/week` показывает тот же текст в Telegram)
**по умолчанию выключен**: включите `WEEKLY_REPORT_ENABLED=true`, и он будет
уходить по понедельникам после `WEEKLY_REPORT_HOUR` (08:00 по Варшаве).
Маркер отправки — `bot-reports/<понедельник>-weekly.json`, поэтому перезапуск
не даёт второй отчёт. В отчёт попадают топ ошибок, MTTR и роботы-кандидаты на
ремонт/замену (`RETIREMENT_MIN_OFFLINES` офлайнов за период).

## Простой роботов в отчёте смены

К отчёту смены (и к `/stats`) добавлена строка про ремонты:

```
🛠 MTTR 3h 06m over 2 repairs · longest #3680 4h 18m
```

Считается по журналу `change_status_robots`: интервалы Offline→Online, которые
закрылись внутри смены (робот вернулся в работу на этой смене), усредняются.
Роботы, которые всё ещё в офлайне, в MTTR не попадают — их простой ещё идёт.
Если журнал недоступен, строки просто нет: отчёт не выдумывает цифры.

## Защита от дублей (один Telegram — один бот)

Telegram long polling допускает только один активный `getUpdates`: апдейт
считается подтверждённым лишь при следующем запросе с бо́льшим offset. Поэтому
два запущенных инстанса (например, локально и на Railway) успевают обработать
одно и то же сообщение дважды — дубли в `exceptions_glpc` и в Lark-группе.

Перед стартом бот занимает лиз в таблице `bot_leases`
(миграция: `sql/bot_leases.sql`):

* свободен или просрочен → инстанс становится опрашивающим;
* занят живым инстансом → процесс уходит в **standby**: `getUpdates` не
  вызывается, сообщения и отчёт за смену он не трогает (отчёт шлёт только
  опрашивающий, иначе были бы двойные отчёты);
* лиз продлевается отдельным потоком и на каждой итерации polling
  (`BOT_LEASE_TTL`, по умолчанию 90 секунд); если продлить не удалось —
  polling останавливается сам;
* при остановке контейнера (деплой, Ctrl+C) лиз отпускается сразу по
  `SIGTERM`, поэтому новый контейнер начинает опрашивать без паузы;
* `/health` показывает роль процесса: `"poller": "poller"` или
  `"poller": "standby (<holder>)"`.
* лиз продлевает отдельный поток (`BOT_LEASE_HEARTBEAT`), поэтому долгая
  обработка фото не приводит к передаче лиза соседу;
* `/health` — это liveness-сигнал: при зависшем или потерявшем лиз
  опросе он отдаёт **503** (`POLL_STALL_SECONDS`), и Railway
  перезапускает контейнер.

Если таблицы нет, бот продолжает работать, но пишет предупреждение в лог: пока
миграция не применена, защиты от дублей нет.

## Что бот удаляет, а что оставляет

| Сообщение | Что с ним |
|---|---|
| Команды сотрудников (`/offline 3680`, `/stats`, `/reg`, `/help`, …) | бот удаляет после обработки |
| Описание причины при `/offline` / `/online` | бот удаляет, **только если статус действительно изменён** |
| Сообщение бота о смене статуса (🤖 Robot 3680 → Offline, причина, кто) | **остаётся** в чате |
| Сообщения об ошибках роботов | **остаются** — их видит смена, они источник записи |
| Подтверждения «✅ Saved / Photo forwarded» | удаляются через `TELEGRAM_CONFIRM_TTL` (10 с) |
| Кнопки выбора причины | удаляются, когда шаг пройден |

Отключается переменной `DELETE_USER_MESSAGES=false`. В личных чатах бот чужие
сообщения не трогает (проверка по типу чата).

Если запись статуса не прошла (база недоступна, ошибка PATCH, робот не
найден), сообщение с причиной **остаётся в чате**, а флоу не теряется: бот
просит повторить причину следующим сообщением, чтобы сотрудник не набирал
текст заново.

## Служебные сообщения бота

Подтверждения (`✅ Saved: robot …`, `✅ Photo forwarded to Lark`, а также
статусы «не смог скачать/переслать фото») бот **удаляет за собой** через
`TELEGRAM_CONFIRM_TTL` секунд — по умолчанию 10, `0` отключает удаление.
Так группа не зарастает «хвостами»: сотрудник видит мгновенную реакцию,
и через десять секунд остаётся только его собственное сообщение.

Важное и обучающее не удаляется: подсказка про `/reg`, подсказка по формату
сообщения, `/help`, `/id`, `/stats`, ответы на команды и алерт
«отправить в обслуживание» (его читает вся смена).

## Смена статуса робота (офлайн/онлайн)

```
/offline 3680
   → бот показывает робота, текущий статус и кнопки причин
   → тап по причине (например 行走异常/Abnormal walking)
   → бот просит описать причину сообщением
   → сотрудник пишет причину
   → бот удаляет свои сообщения, меняет статус в базе
     и отправляет карточку в Lark-группу
```

Что пишется в базу (туда же, куда пишет приложение склада):

| Таблица | Что |
|---|---|
| `robots_maintenance_list` | `status` = `在线 \| Online` / `离线 \| Offline`, `updated_at`, `updated_by` |
| `change_status_robots` | журнал: `old_status` → `new_status`, `type_problem`, `problem_note`, `robot_id`, `add_by`, `warehouse` |

Причины берутся из вашего же журнала (кнопками, чтобы данные не разъезжались):
в офлайн — `行走异常/Abnormal walking`, `小车车身部件撞坏/Damaged car body parts`,
`Safety controller issues`, `其他 / Other`; в онлайн — `Solved without changing`,
`更换备件 / Replaced Spare Parts`, `软件升级 / Software Upgrade`, `Software fix`, `其他 / Other`.

Детали: может любой сотрудник с привязкой `/reg` (автор пишется его `card_id` из
`employees`); если робот уже в этом статусе — бот откажет и покажет текущий;
меняются только роботы склада `GLP-C`; незавершённый флоу живёт
`TELEGRAM_STATUS_FLOW_TTL` секунд (по умолчанию 300) и сбрасывается командой
`/cancel` или любой другой командой.

## Надёжность

Что бот делает, чтобы не терять сообщения и не падать:

* **offset Telegram сохраняется** в Supabase Storage (`bot-state`): после
  перезапуска уже обработанные апдейты не приходят повторно (дублей нет);
* **дедупликация** — по паре `(chat_id, message_id)`, а метка «обработано»
  ставится только после успешной обработки: разовый сбой БД не «съедает»
  сообщение;
* **ошибка чтения БД не выдаётся за «смену без исключений»** — отчёт и
  `/stats` честно сообщают о проблеме, а отчёт повторяется в следующем цикле;
* **любая ошибка Lark-вебхука** (таймаут, не-JSON) не роняет обработку:
  срабатывает текстовый fallback, а не потеря карточки;
* **длинные тексты обрезаются** перед отправкой (Telegram — 4000 символов,
  значения в карточке — 500);
* **старые фото удаляются** (`IMAGES_RETENTION_DAYS`), скачиваемые файлы
  ограничены по размеру (`TELEGRAM_MAX_FILE_MB`);
* **`/health`** отдаёт 503 при зависшем опросе, поэтому Railway
  перезапускает контейнер.

## Формат сообщения об ошибке

```
<issue type>: <description>. <robot number>
```

Пример:

```
Unable to drive: Security module failure. 3780
```

Порядок обработки: проверка привязки → разбор формата → проверка, что номер
робота состоит из цифр → запись в Supabase (с фаззи-поиском шаблона) →
пересылка карточки в Lark → при `count >= ERROR_THRESHOLD` алерт
«отправить в обслуживание».

Если робота нет в `robots_maintenance_list` (склад `GLP-C`), запись в базу
невозможна — номер ставится в очередь `robots_to_add`. Но сама ошибка **всё
равно уходит в Lark-группу** обычной карточкой (без строки со счётчиком смены):
смена видит проблему, а не теряет её. Факт «робота нет в системе» в Lark не
пишется — об этом бот сообщает только сотруднику в Telegram.

## Ссылки на фото

Фото уходит в Supabase Storage, а в сообщениях показывается **короткая
ссылка** нашего домена:

```
https://glpc-bot-lark-production.up.railway.app/p/tg_AQADox9rGxg5oEl-.jpg
```

Эндпоинт `/p/<файл>` отдаёт 302 на подписанный URL Supabase, поэтому bucket
остаётся приватным. Успешные подписи кэшируются на час, а «такого файла нет» —
на `SIGNED_URL_MISS_TTL` секунд (по умолчанию 300): без негативного кэша перебор
имён файлов дёргал бы Storage на каждый запрос. Если Storage недоступен,
`/p/<файл>` отдаёт 503, а не 404 — иначе битая ссылка закэшировалась бы
у клиента навсегда. Домен задаётся `PHOTO_LINK_BASE`, а `PUBLIC_PHOTO_URLS=true`
переключает на публичные ссылки Supabase (bucket переводится в public явным
запросом) — они не зависят от работы бота.

## Фото и запись об ошибке (сейчас выключено)

Привязка фото к записи об ошибке реализована, но **по умолчанию выключена**
(`PHOTO_ATTACH_ENABLED=false`): фото просто уходит в Lark-группу с подписью
«📷 Photo from …», как раньше. Поиск номера робота по самому фото (OCR) не
делается.

Если включить флаг `PHOTO_ATTACH_ENABLED=true` (и выполнить
`sql/exception_photo.sql`), сотрудник сможет присылать текст ошибки и фото
в любом порядке, а бот соберёт это в **одну запись**:

| Как пришло | Что делает бот |
|---|---|
| Фото **с подписью** вида `Unable to drive: Security module failure. 3780` | создаёт запись (номер и текст из подписи) и прикрепляет фото |
| Текст ошибки, **потом** фото (в течение `PHOTO_ATTACH_WINDOW`, по умолчанию 10 мин) | прикрепляет фото к последней записи этого сотрудника |
| Фото, **потом** текст (в течение `PHOTO_HOLD_SECONDS`, по умолчанию 90 с) | держит фото и при создании записи прикрепляет его |
| Фото без текста и без соседней ошибки | через `PHOTO_HOLD_SECONDS` пересылает фото отдельно (как раньше) |

Фото уходит в Supabase Storage, а в записи сохраняется ссылка в колонке
`photo_url` (миграция: `sql/exception_photo.sql` — добавляет колонку в
`exceptions_glpc` и `exceptions`). В Lark отправляется **одно** сообщение:
карточка ошибки вместе с фото (картинкой, если квота Lark позволяет, иначе
ссылкой). Номер робота берётся из подписи или из соседнего сообщения; OCR по
самому фото пока не делается.

## Фотографии

Фото из Telegram скачиваются в `images/` и уходят в Lark-группу двумя путями:

1. **Картинкой** (штатный): загрузка в Lark `im/v1/images` → вебхук шлёт
   `post` с картинкой и подписью «📷 Photo from <имя>». Это **единственный**
   вызов, расходующий квоту Open Platform — 1 на фото.
2. **Ссылкой** (автоматический резерв): если Lark API ответил ошибкой
   (например, `code 99991403 This month's API call quota has been exceeded`),
   фото грузится в Supabase Storage (`bot-photos`) и в группу уходит текст с
   подписью и ссылкой. Квота Lark не расходуется вообще.

Бот сообщает в Telegram, каким путём ушло фото:
`✅ Photo forwarded to Lark` или `✅ Photo sent to Lark as a link`.

Bucket создаётся автоматически при первой загрузке; настройки —
`SUPABASE_PHOTO_BUCKET`, `SUPABASE_PHOTO_BUCKET_PUBLIC`,
`SUPABASE_SIGNED_URL_TTL` (приватный bucket + signed-ссылка по умолчанию,
чтобы фото не были публично доступны).

## Диагностика

| Симптом | Причина / решение |
|---|---|
| `TELEGRAM_BOT_TOKEN is not set` | не заполнен `.env` |
| `Can't reach Telegram with the configured token` | неверный токен |
| `⚠️ Can't save the link right now` | не выполнена `sql/telegram_users.sql` |
| `/health` → `"users_table": false` | таблица `telegram_users` не создана (бот скажет об этом и в консоли при старте) |
| `code 99991403` в логах | квота Lark исчерпана — фото уйдут ссылкой, остальное работает |
| `⚠️ Employee ... not found` | имени нет в `employees.user_name` — проверить написание |
| Бот молчит в группе | бот не админ группы, либо сообщение не из топика `Ex GLPC` |
| `I can't identify this topic yet` | не задан `TELEGRAM_TOPIC_ID` — сделать `/id` в топике и вписать id |
| `Conflict: terminated by other getUpdates` | запущено два инстанса (Railway + локально) |
| Фото не уходит в Lark | не заданы `LARK_APP_ID`/`LARK_APP_SECRET` или кончилась квота |

Логи: stdout (Railway) и `logs/app.log` (ротация 5 МБ × 5).
